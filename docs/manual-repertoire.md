# 本人录谱、纳入训练与冻结发布

这组代码来自棋谱屋实际使用的录谱与训练后端。它提供可单独运行的领域模块和合成测试，不打包完整网站界面、引擎推荐或个人训练材料。

录下一步只会保存草稿。使用者必须明确把这一步纳入训练；发布时，只把已经纳入且能走到终点的完整分支冻结为一个版本。以后修改草稿，不会改变旧版本或已开始的练习。

```text
标准初始局面 → 手动录制双方 → 逐边选择纳入 → 检查所有选中分支 → 发布
                                                             ↓
                    选择执红/执黑 ← 冻结版本 → 按实际路线走对手应手
```

- 一份录谱允许多个后继答案，也允许返回较早局面补录分支。
- 相同棋盘的不同来路保留不同的完整历史；转序索引只帮助查看，不自动复制纳入选择。
- 默认终点是10回合，也可明确标记较早的分支终点。缺少后续的选中分支不能作为完整训练发布。
- 练习中，对手只走该发布版本内的选中边，其选择在本轮冻结。
- 本方走出没有纳入的合法着时，本次复现失败；这不是棋步质量评价。非法操作不计失败。
- SQLite事务、修改版本检查和持久请求回执用于处理并发、刷新和重试。旧回执重发不会重复推进当前练习。

## 运行合成示例

Python 3.10+，只需要标准库：

```bash
python -B examples/manual_repertoire_demo.py
python -B -m unittest discover -s tests -v
```

示例只录制双方几步兵，不是教学定式或真实棋局。数据库保存在临时目录，示例结束后自动清除。测试中的20半步宫内往返同样是专门构造的规则测试，不表示值得学习的线路。

## 公开范围

后端入口是 `app/repertoire_training.py` 的 `Service`。录谱操作为 `editor_create/update/record/toggle/terminal/publish`；训练沿用 `start/move/abandon`。`GET`只读，不初始化数据库。数据库由第一次明确的写操作在调用方指定目录内创建。

发布版本、草稿和个人进度需要在实际部署中备份。此仓库不含任何个人数据库、对局、答案、报告、引擎收据、引擎/NNUE、实验材料或第三方棋盘。纯规则依赖检查棋子几何和将帅安全；完整重复/长将规则裁决、棋步优劣、推荐与学习效果都不由该模块证明。

精确提取边界及原函数hash见[源码来源](manual-repertoire-provenance.md)。

## 编辑控制器的自动参考请求

`Controller`先读取已有参考；当前上下文尚未核验时自动提交推荐请求，并读取后台进度。暂时失败或仍无候选时按有界重试恢复，每次访问最多自动提交三次；达到上限后仍可录谱，返回该局面会重新尝试。已核验缓存不重复发起搜索。推荐请求有独立的取消和状态管理，等待推荐时可以切换节点或记录着法；旧节点迟到的结果不会覆盖当前局面。调用方可以用`automaticRecommendations:false`关闭自动请求。

状态回调为`changed(state, kind)`：普通编辑通知的`kind`为`editor`，推荐读取/计算通知为`recommendations`。调用方可以据此只刷新推荐区域，保留棋盘、分支按钮和焦点。渲染回调异常通过可选的`onRenderError(error, kind)`报告，不会留住编辑操作的忙状态。默认计时器取消封装保留浏览器调用语义；请求切换和隐藏页面继续遵守原有并发保护。

这里公开的是注入API的客户端协议；引擎、后台调度、完整网站和计算收据均不随此精选组件提供。自动参考不会勾选训练答案。合成控制器测试可运行`node --test tests/editor-controller.test.cjs`。

## 误录分支移除与恢复的客户端协议

控制器新增`removeBranch(nodeId)`和`restoreBranch(branchId)`。移除只针对所选节点及其全部后继，同级分支不在范围内；`branchSummary(view, nodeId)`返回该子树的节点数、已纳入着数和上一步，供宿主界面在操作前展示影响范围。根节点不能移除。取消训练纳入与移除草稿分支仍是两个独立动作。

`editor_remove_branch`发送`{id, revision, node_id, request_id}`；`editor_restore_branch`发送`{id, revision, branch_id, request_id}`。调用方的后端应把完整子树及原纳入/终点设置存入可恢复记录，并在移除回执中返回`removed_branch.id`。恢复不能覆盖后来重新录入的同一着法；上一步也已移除时，应先恢复包含上一步的分支。已发布版本与已开始训练的快照不随草稿移除或恢复改变。

两个操作都使用持久的请求编号。回应丢失后，控制器保留原请求，刷新后可用`retry()`原样重发，宿主后端应按同一`request_id`返回原回执而不重复操作。控制器随后读取最新草稿；若旧回执选中的节点已经移除，只有明确的`node_not_found`会改读起点，其它读取失败继续显示为失败。

`undoRecord()`是最近误点的快捷撤销，仅允许本次新录、尚未纳入且没有后继的叶子，且草稿版本仍一致；重访已有着法、已纳入节点、已有后继或版本变化均不能通过此快捷入口移除。该动作也走可恢复的分支移除协议。

本轮仅公开控制器协议与合成测试，完整界面和新增移除/恢复后端仍在本地产品中。仓库原有后端精选快照不会因此自动具备新接口；接入这些方法时，宿主服务需要实现上面的版本、幂等与快照契约。
